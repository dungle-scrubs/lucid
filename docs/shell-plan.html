The shape

One long-running daemon on 17428 hosts every session in-process, keyed by artifact path, and serves the shell. The shell is the chrome — it swaps the active session's review panel and artifact iframe. Session data is read and written in place — the daemon opens, appends to, and watches each log where it already lives (<project>/.lucid/<name>/log.ndjson), exactly as the per-session server does today. No copy, no migration, no central database; only a pointer registry is central.

Server model — decided: B, one running server

Chosen: a single long-running daemon on 17428 hosts every session. No per-session processes, no port rotation, one origin — so the cross-origin edge below is gone. A is kept here only as the road not taken.

A · additive hub  ·  not taken

Keep today's per-session processes untouched; the hub is a thin coordinator that registers them and serves the shell. Least change to the server core. But the shell then talks cross-origin to N session ports — needs a proxy or an allow-list.

B · one running server  ·  chosen

Fold every session into a single long-running daemon on 17428 — no per-session processes, no port rotation, one origin. lucid open registers a session with the daemon instead of spawning one. Dissolves the cross-origin problem entirely and makes the multi-session store natural. Cost: a deeper refactor of the session lifecycle, and shared fate — one daemon owns every session's liveness, watcher, and log.

The shell and the server become one thing, and the rotating-port problem disappears rather than being worked around. The one trade-off accepted with B: crash isolation — today a wedged session can't take the others down; under B they share a process, so the daemon's own robustness matters more.

Isolation & lifecycle — nothing bleeds

The key that keeps sessions apart today carries over unchanged: a session is its canonical artifact path. The log lives at <artifactDir>/.lucid/<name>/log.ndjson, and every command already names its file. Two artifacts — same project or different — are different paths, so they cannot collide.

  • Cross-project: the boundary is the path, not the project. A project is just a directory grouping (how the shell clusters tabs). Different projects are different paths, isolated by construction.
  • CLI addressing: lucid wait <file>, lucid ask <file> each name an artifact. Under B the CLI talks to the one daemon and addresses the session by path — there is no ambient "current session" to leak into. A command touches exactly the path it names, as it does now.
  • The daemon is a cache, not the truth. Each session's on-disk log stays the source of truth (as today). The daemon loads a session's folded state + watcher on demand and evicts it when idle; restarting it loses nothing.
  • One origin, still boxed per project (grilled). Every artifact and asset route is namespaced by an opaque session id — /s/<id>/… — and the daemon resolves each against that session's own artifactDir with the exact resolveAsset confinement used today (traversal / dotfile / symlink-escape rejected). One session's page can never read another's project files; there is never a shared filesystem root, and raw absolute paths never appear in URLs.
  • Data stays in the project folders. Under B only the server relocates — the artifact and its .lucid/<name>/ (log, versions, pasted images) stay colocated in each project, exactly where they are now. The daemon reads and writes them in place. The only central file is ~/.lucid/registry.json, and it holds pointers only (paths, last-seen), never session data. Nothing is centralized or copied out of the project.
  • Lifecycle maps one-to-one with what you already handle — folded from each log, plus liveness: active (loaded, attended) · suspended (known, evicted from memory; reactivate = reload) · ended (lucid end) · dormant (on disk, surfaced by the ~/dev scan). Under A "live" means a bound port; under B it means "loaded in the daemon" — same states, different signal.

Net: B relocates the server; it does not change the data model or the isolation key. Everything already reasoned about — multiple per project, stale, reactivated — holds, because it all lives in the per-session logs.

Decisions locked

  • Unified multi-session chrome — the shell is the chrome, not an iframe host. One header, real tabs, shared state. Accepts the single-session store refactor.
  • Discovery — scan ~/dev recursively for dormant sessions; live sessions register on open for instant updates. Roots configurable, ~/dev the default.
  • Command bar — cmdk (the headless engine behind shadcn's Command), styled to Lucid's ink/brass tokens rather than importing shadcn wholesale.
  • One entry URL — 127.0.0.1:17428 installed as a Chrome app gives a permanent Dock icon that never goes stale on a rotating session port.
  • Agent interaction — unchanged (grilled). The consuming agent keeps the tiny per-file loop (open → wait → ask → end); multi-session is the human's shell only, never the agent's concern. B's payoff for the agent is invisible: no per-session server to spawn, instant resume against the always-up daemon, and open surfaces the session as a new tab in the running shell instead of a new browser window.
  • UI state — layout global, marks per-session (grilled). Panel width and sidebar open/closed are one shell-level setting shared across tabs; the show-marks toggle is remembered per session, keyed by session id in the store.
  • The daemon never spawns agents (grilled). D-064 holds: the daemon only hosts sessions and serves the shell; it never re-invokes an agent. Agent-spawning stays in the separate, opt-in, human-run fork launcher. A fork under B just registers its child session with the daemon, so the new artifact appears as a tab — spawning is unchanged and never migrates into the always-on server.
  • Daemon lifecycle — self-managed, supervision out of scope (grilled). First lucid open auto-starts the daemon if it is down; it stays up (does not idle-exit the way per-session servers do), while individual sessions still evict from memory when idle. Service supervision (LaunchAgent, systemd, etc.) is deliberately kept out of the codebase — the daemon is a plain long-lived process anyone can supervise however they like. Nothing machine-specific ships in Lucid; the operator wires their own supervisor externally if they want one.

The roadmap — five phases

PHASE 0

The daemon & registry

shipped

The backbone — independently useful, and it powers the Chrome-app Dock icon even before the shell exists.

  • One daemon on 17428 that hosts sessions in-process (folded state + file watcher per open session, keyed by artifact path), serves the shell, a /sessions list, and an SSE stream of registry changes.
  • lucid open <file> registers the artifact path with the daemon, which loads it from its on-disk log; ~/.lucid/registry.json persists the pointer index. No ports or pids to spawn or prune.
  • Seeds from a recursive scan of ~/dev so dormant sessions are listed too.
  • Exit: curl the daemon and see every live and dormant session across the machine, each hosting from its own project folder.
PHASE 1

Session-keyed chrome

the hard core

Turn the single-session store into a multi-session one. This is the load-bearing refactor; everything visual rides on it.

  • Store becomes a map sessionId → { … }, with one active session driving the render. Per session it holds the folded state — the current view derived by folding that session's event log (its annotations, conversation, current version, status) — and its stream, the live SSE connection that pushes new events into that fold — plus staged highlights and drafts.
  • Actions and the EventSource (the stream) become session-scoped rather than module-global singletons.
  • Exit: same single-window experience as today, but internally multi-session-ready (still one session shown).
PHASE 2

Tabs & multi-stream lifecycle

needs 0 + 1
  • A tab bar bound to the registry. Opening a tab connects that session's SSE + REST; closing disconnects.
  • Switching tabs swaps the active session — state already loaded, so the switch is instant.
  • Manage live streams with a hard cap of 10 open sessions (decided); beyond that, evict the least-recently-used stream from memory (its log is untouched, so reopening refolds instantly).
  • Per-session attention tags in the tab list (requested) — each tab shows when something is new or waiting on you: an unanswered question, a fresh agent reply, a new version. You can tell at a glance which review needs you without opening it.
  • Exit: multiple sessions open at once, one window, switch without a reload, and attention tags that pull you to the tab that needs input.
PHASE 3

⌘K command palette

needs 0
  • cmdk, fuzzy over every registry session plus actions: open a tab, new session, approve, jump to an annotation.
  • Styled to Lucid's tokens — cream-on-dark palette, mono for paths, no second accent.
  • Exit: ⌘K from anywhere finds and opens any session on the machine.
PHASE 4

Polish & the Dock app

finish
  • Install 17428 as a Chrome app; icon, empty states, keyboard model, focus routing, reconnection.
  • Cross-session niceties: unread/attention badges per tab, "N agents listening" across sessions.
  • Exit: a Dock icon that opens one window onto everything.

Risks — settled

Cross-origin is the sharpest edge.  Resolved by B.

Would have been the sharpest edge under A (strict validateHeaders host/origin checks blocking the shell's cross-port fetches). B is one origin, so it never arises. No longer an open question.

Keyboard model — recommended map.

The in-session Sessions panel is subsumed by the shell's tab bar + ⌘K, so it goes away and frees its shortcut. Proposed map: ⌘K command palette · ⌘1–⌘9 jump to tab N (editor convention) · ⌘⇧[ / ⌘⇧] prev/next tab · ⌘B toggle the review panel (unchanged) · ⌘. toggle marks (unchanged) · ⌘⏎ send / approve (unchanged). No collision, since ⌘1/⌘2 are no longer panel-switchers.

N live SSE streams.  Decided: cap at 10.

Open tabs are capped at 10. Beyond that, the least-recently-used session's stream is evicted from memory; its on-disk log is untouched, so reopening refolds instantly. You won't hit the cap, but it bounds the process.

Everything in one surface — a risk with a recommendation, not an open question.

One window over every project is a bigger blast radius (a stray approve on the wrong tab; unrelated repos side by side). Recommendation, not a decision I need from you: a per-tab confirm on destructive actions (Approve, End), and clear project labeling on every tab so the active session is never ambiguous. I'll build it that way unless you object.

What I'd build first

Start with Phase 0 — the hub and registry. It is self-contained, low-risk, independently useful (it fixes the rotating-port Dock-icon problem on its own), and it unblocks everything else. I would settle the cross-origin question in parallel, since it decides the phase-1 store design.
