# HCN failure semantics and correction channels

Produced by Codex, primary agent, inline research on 2026-09-11. Scope: documented contracts and the cited artifact rejection path. Lucid source citations name an unpublished local commit; use the local repository to inspect them. No unrelated local commits are published with this report. This report does not claim live recovery parity across harnesses or an exhaustive Lucid failure inventory.

## Finding that changes the design

**Documented:** HCN's `retryable` flag is not a classification of whether an agent can adjust its action. The owning README marks rejected options non-retryable across the model chain while explicitly describing changed options as the remedy. Lucid needs a separate recovery decision that considers authority, agent availability, and the failed operation. [HCN failure taxonomy](https://github.com/dungle-scrubs/harness-cli-normalizer/blob/2e19ca2abdfc877a6a373941def104c175f2faca/README.md#failure-taxonomy).

## Ownership and the existing rejection

**Documented:** HCN normalizes harness interfaces and supervises one process; durable coordination across process boundaries belongs to its caller. [HCN scope ADR](https://github.com/dungle-scrubs/harness-cli-normalizer/blob/2e19ca2abdfc877a6a373941def104c175f2faca/docs/adr/0007-narrow-scope-one-process-at-a-time.md). Recovery attempt identity, restart handling, and final work completion therefore need a Lucid-owned decision; any native delivery additions belong behind HCN's interface.

**Documented in source:** The artifact rejection handler emits a nonterminal error to Lucid's sequencer when storage refuses an update. The output pump then carries the original message and settles the turn on its completion event. This path records the failure rather than scheduling corrective model input. Artifact handler: local Lucid commit `837bd6c8b429879a36f8b2e6a186e70cb5f10542`, `src/modes/host.ts` (L459-L478), output pump: local Lucid commit `837bd6c8b429879a36f8b2e6a186e70cb5f10542`, `src/modes/host.ts` (L1470-L1497).

**Observed:** Before charting, a direct invocation of Lucid's current `checkWebLink` for the RAND citation returned `{"reason":"HTTP 403","status":"unverified"}`. A disposable record using `writeArtifact` with an injected 403 result retained version 1, refused version 2 with `artifact-link-unverified`, and had no stored version 2. These observations establish the refusal, not a live correction loop. The owning policy explicitly refuses uncertain HTTP outcomes. Link admission contract: local Lucid commit `837bd6c8b429879a36f8b2e6a186e70cb5f10542`, `docs/artifacts.md` (link-navigation-and-validation).

## Unverified guarantees and next decisions

- **Unverified:** receiving correction context and producing a successful correction on each installed harness/mode. No live model run was performed. The channel primitives are documented; the end-to-end behavior needs later deterministic implementation proof and bounded live confirmation.
- **Unverified:** full native tool-result replacement or immediate in-turn injection through the common HCN surface. The reviewed session protocol documents text send and answer, not a portable tool-result response operation. This is a limitation of the reviewed contract, not proof that no native harness can support it.
- **Open design decision:** complete Lucid failure classification, payload bounds and redaction, exact retry budgets, receipt durability, cancellation, uncertain side effects, and presentation. The remaining child tickets own these questions.
- **Contract conflict to resolve:** current artifact admission rejects unverified links, and existing headless interaction handling stops unsupported blocking requests. The new recovery policy must specify permitted adjustment and terminal escalation for both, rather than suppressing notices alone.

The documentation questions are answered to their stated standing. Native transport parity and complete failure coverage remain explicit verification work for later decisions, not claims from this research.
